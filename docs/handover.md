## 3. Как работать с Fil

**Формат ответов.** По-русски. Структурированно, без воды и вступлений. Короткие абзацы. Таблицы там, где сравнение. Не заваливать текстом.

**Порядок работы:** сначала полностью формируем идею, только после явного подтверждения — технический план. Не выдавать план реализации до закрытия этапа идеи.

**Формат интерфейса Claude Code.** Он часто задаёт вопросы кнопками — Fil может только выбрать вариант или написать в поле «Type something». Если ответ сложнее выбора, надо давать текст для этого поля.

## 4. Суть проекта

**Не хранилище. Механизм возврата.**

Проблема: человек не может держать всё в голове. Он сбрасывает мысли, идеи, события — и они пропадают, потому что записать легко, а вернуться некому. 95% записанного не открывается повторно никогда.

Система возвращает: напоминает о том, что человек сам себе обещал, вытаскивает старую мысль в нужный момент, показывает противоречия с самим собой, отслеживает прогресс к целям, которые он сам назвал.

**Главная ценность (раздел 1.1 vision.md):** механики возврата и развития — напоминания, подведение итогов, отслеживание прогресса, техники развития, мотивация. Именно они требуют максимального качества и по ним судится, удался проект.

**Интеграции (Notion, Google Calendar) — второстепенные фишки.** Их качество не критично.

Практическое следствие: Фаза 4 приоритетнее Фаз 5 и 6.

## 5. Приоритеты Fil — в порядке важности

1. **Качество и удобство пользователя.** Система должна быть приятной, а не просто работающей
2. **Понимание.** Уметь объяснить любой модуль голосом, включая трейдофы
3. **Скорость.** Но не ценой первых двух
4. **Экономия.** Порог: до ~$1/мес добавки — не обсуждается, свыше $2/мес — приносить варианты с числами

**Что раздражает:** скучное, неоригинальное, шаблонное. «Просто напоминалка» — приговор. Система должна давать то, чего не даст блокнот.

**Чего не хочет:** быть наблюдателем за работой Claude Code. Отсюда карта вовлечённости 🔴/🟡/⚪ и правило «тесты формулирую я, реализацию пишет он».

## 6. Главный повторяющийся урок

**За две недели найдено больше двадцати дефектов. Все одного класса: проверялась не реальность, а её удобная версия.**

Список, чтобы был понятен масштаб:
- модель снята из API, а список моделей заявлял её рабочей
- задания молча удалялись после исчерпания попыток
- напоминания работали только для текста, не для голоса
- парсер знал только цифры; тесты писал автор парсера — тоже цифрами
- «7:40 вечера» разбиралось как утро
- апдейты Telegram терялись через раз из-за гонки
- триграммы не работали на кириллице — канал был мёртв с первого дня
- полнотекст требовал все слова разом, recall был 0.00
- `TRUNCATE` обходил защиту записей
- вечерний разбор повторял одну пачку семь вечеров подряд
- замеры тем делались пачками, а воркер работает по одной
- смена вопроса петли не вызывалась в продакшн-коде ни разу
- набор тестов был красным три дня, и этого не заметили

**Правила, выведенные из этого (в CLAUDE.md):**
- замер обязан воспроизводить рабочий режим, иначе он врёт
- тест на функцию не заменяет теста на путь
- там, где вход приходит из внешнего мира (речь, ответ провайдера, доступность модели) — проверять на настоящем входе
- зелёный набор тестов означает только, что код делает задуманное автором

**Следствие:** фаза не считается сделанной, пока ею не пользовались неделю.

## 7. Где сейчас

**Фазы 0–4 написаны, ни одна не закрыта.** Критерий закрытия — измеренная метрика, а не работающий код.

Работает: приём текста и голоса, расшифровка, напоминания на естественном языке, приватный режим, гибридный поиск, разметка по смысловым единицам, утренняя сводка, вечерний разбор, всплывание старого, петли, дела, пауза.

**В работе прямо сейчас: Волна 1** — исправление того, что вскрылось за неделю использования. Десять задач, свежий субагент на каждую. Подробности в `docs/revision_after_use.md`.

Корневая причина Волны 1: **система извлекает, но нигде не формулирует.** Всё, что видел пользователь, — куски его же речи, обрезанные по счётчику символов. Причина — решение Фазы 4 «ноль вызовов модели», отменено.

## 8. Что решено и не переспаривается

Пятнадцать ADR. Ключевое:

| Решение | Почему |
|---|---|
| Postgres как единственное хранилище | транзакции: запись, вектор и задание пишутся вместе. Отдельная векторная БД и Redis отклонены |
| Очередь в Postgres (pgqueuer) | инвариант 7: запись и задание одной транзакцией, sweep не нужен |
| `entries` только на вставку | два триггера: строковый и операторный на TRUNCATE |
| Приватность без шифрования | tsvector рядом с шифротекстом — театр; ключ вне сервера ломает автоподъём |
| Приватные записи только текстом | расшифровка идёт наружу; протекающая приватность хуже отсутствия |
| Прямые вызовы API, без SDK и LangChain | конвейер детерминированный, агентов нет; абстракции скрыли бы механику |
| Gemini на всё (STT, эмбеддинги, разметка) | один провайдер, один ключ; дорогой тир (Claude Sonnet) с Фазы 6 |
| Эмбеддинги 768 через MRL | 98% совпадения с полной размерностью; смена = переиндексация архива |
| Три канала поиска + RRF | вектора не находят имена, полнотекст не понимает смысл, триграммы чинят опечатки речи |
| Разметка по смысловым единицам | одно голосовое содержит мысль, решение и задачу разом |
| Согласие двух прогонов вместо самооценки | 29 из 29 «уверен» на мусоре — самооценка не калибрована |
| Дословный текст хранится, показывается вычищенный | чистку делает модель, модель ошибается; оригинал невосстановим |

**Правило:** принятое решение не переспаривается в чате. Несогласие — новый ADR, старый получает блок «Обновление».

## 10. Как принимаются решения

**Замером, а не рассуждением.** Каждый раз, когда возникает «мне кажется, лучше так» — вопрос переводится в число. Примеры из практики:
- нужны ли триграммы → прогнать eval с весами 1/1/0 и 1/1/1
- 768 или 1536 → замер совпадения выдачи
- какая модель для чистки → eval на архиве, не по прайсу
- порядок блоков в сводке → посмотреть на себе несколько дней

**Fil выбирает, Claude Code даёт варианты с трейдофами.** В 🔴-областях он не решает молча.

**Цена решения записывается явно.** В каждом ADR есть раздел «чем платим» — это то, что придётся терпеть.

## 11. Стиль общения с системой (для пользователя)

Это записано в `vision.md §7.0`, но стоит помнить при любой правке:

1. Сообщение даёт, а не требует. Требование допустимо, только если пользователь сам просил
2. Запрещён ретроспективный упрёк — сообщение о том, что не сделано
3. Нечего дать — молчим; факт молчания виден в `/status`
4. Время под контекст дня, кроме утреннего якоря 09:00
5. Ни стриков, ни счётчиков, ни процентов
6. Первая неделя должна дать ощутимое

Основание: усталость от уведомлений — главная причина ухода примерно у 38% пользователей. Формирование привычки занимает 18–254 дня, медиана около 66 — систему бросают в этой яме.
