# Технический план

**Проект:** персональный ассистент (см. `vision.md`)
**Дата:** 12 августа 2026 · решения раунда 1 внесены (см. `answers_round1.md`)
**Уточнено 15 августа 2026:** модель эмбеддингов выбрана; дорогой тир откладывается до Фазы 6; два бота Telegram.
**Версии проверены:** 12 августа 2026 по PyPI и сайтам поставщиков. Всё, что помечено ⏳, перепроверять раз в квартал.

---

## 0. Главное правило проекта

**Это не проект «Claude пишет, я смотрю».** Скорость важна, но не ценой понимания.

Критерий успеха: через полгода я могу открыть любой модуль и объяснить голосом, что он делает, почему сделан так, и какие альтернативы отклонены. Если не могу — проект провалился, даже если работает.

Механики, которые это обеспечивают, — в разделе 7. Они не опциональны.

**Сроков нет.** Фаза закрывается по критерию готовности, а не по календарю.

**Начинаем с минимума.** Не закладываем запас «на будущее»: самый дешёвый работающий вариант, упёрлись — увеличили. Касается сервера, моделей, индексов, всего. Из этого правила выросли три решения: STT через API вместо своей модели, очередь на Postgres вместо Redis, младший тариф VPS.

## 1. Архитектура

Четыре слоя плюс наблюдаемость. Каждый тестируется отдельно, каждый можно заменить не трогая остальные.

```
[ Адаптеры ]     telegram (aiogram, polling) · позже web/CLI
       ↓          вызывают сервисы ядра, не лезут в БД напрямую
[ Ядро ]
   ingest        приём события, дедупликация, постановка задания
   stt           расшифровка голоса — внешний API за собственным интерфейсом
   enrich        LLM-разметка: тип, сущности, теги, темы
   memory        запись/чтение, провенанс, оверрайды
   retrieval     гибридный поиск: BM25 + триграммы + вектора + фильтры
   scheduler     один рабочий цикл: разовые задания, напоминания, cron
   digest        сводки, недельное ревью
   llm           единая обёртка над провайдерами: маршрутизация, ретраи, логи, стоимость,
                 сборка блока правил, отсечение приватного.
                 Интерфейс двухтирный (cheap|expensive) с первого дня;
                 на старте зарегистрирован только cheap = Gemini Flash-Lite
       ↓
[ Интеграции ]   Google Calendar · Notion
       ↓
[ Хранилище ]    PostgreSQL — реляционка, полнотекст (tsvector), триграммы (pg_trgm),
                 вектора (pgvector) и очередь заданий. Больше ничего нет
       ↓
[ Наблюдаемость ] стоимость, латентность, назначение вызова
```

**Одно хранилище на всё.** Postgres держит данные, поиск и очередь. Ни Redis, ни брокера сообщений, ни отдельной векторной БД: меньше компонентов — меньше точек отказа, дешевле сервер, и очередь можно писать в одной транзакции с данными (см. инвариант 7).

### Инварианты (нарушать нельзя, проверяются на ревью)

1. Адаптеры не обращаются к БД напрямую — только через сервисы ядра.
2. Прямых вызовов SDK провайдера вне `core/llm` (и `core/stt` для аудио) нет.
3. Таблица `entries` только на вставку. Обновления и удаления запрещены на уровне прав БД. Смена состояния — строкой в `entry_overrides`.
4. Любая производная запись хранит `source_entry_id`.
5. Записи с `is_private=true` никогда не попадают во внешний API: ни в LLM, ни в эмбеддинги, ни в STT, ни в Notion. Проверка на уровне `core/llm`, `core/stt` и `integrations`, а не на уровне вызывающего кода. Исключений нет: в приватном режиме голосовые не принимаются вовсе (расшифровка внешняя), бот отвечает «приватный режим — только текст».
6. Никаких секретов в коде. Только переменные окружения.
7. **Долговечность записи.** Запись в `entries` и задание в очередь пишутся **одной транзакцией**. Либо есть и то и другое, либо ничего: потерять задание при живой записи технически невозможно, поэтому подчищающий sweep не нужен. Это главная причина, по которой очередь живёт в Postgres, а не во внешнем брокере.
8. **Связи считаются без вызова модели** — чистая векторная близость. Вызов LLM в пути «на каждую запись» не появляется.

### Очередь: почему pgqueuer (ADR-0005)

Требования тривиальные: разовые задания, отложенные по времени, повторяющиеся по расписанию, ретраи, один воркер. Всё это — `FOR UPDATE SKIP LOCKED` плюс цикл.

Рассматривались три варианта:

| Вариант | За | Против |
|---|---|---|
| **pgqueuer** 0.26.1 — **выбран** | asyncio, `SKIP LOCKED` + `LISTEN/NOTIFY`, cron из коробки, лёгкая; живёт на том же драйвере, что и приложение | моложе и беднее функциями, чем procrastinate |
| procrastinate 3.9.0 | зрелее, богаче | тянет `psycopg[pool]` — либо второй драйвер БД рядом с asyncpg, либо переводить на psycopg3 весь слой SQLAlchemy |
| свои ~100 строк | ноль зависимостей | ретраи, блокировки и расписание пишу и отлаживаю сам |

**Решающий аргумент:** второй драйвер БД ради очереди на два десятка заданий в день не оправдан. Функциональная разница между библиотеками на такой нагрузке не проявляется, а лишний драйвер — это навсегда.

**Бюджет RAM (4 ГБ):** Postgres ~512 МБ · приложение ~400 МБ → около гигабайта. Запас есть: тяжёлых процессов на сервере не осталось.

### Чего сознательно НЕ берём

- **Локальный STT (Parakeet ONNX INT8)** — около 2 ГБ RAM на инференсе, то есть тариф вдвое дороже; медленнее API на двух общих vCPU; приватностью не оправдан, потому что текст всё равно уходит в LLM. Плюс у ходовой INT8-сборки качество рушится на аудио длиннее 20–30 секунд. Решение обратимо: слой за интерфейсом.
- **Redis + ARQ** — лишний компонент, лишняя память и невозможность транзакционной постановки задания. Вдобавок ARQ (0.28.0) переведён в maintenance-only mode. Postgres уже есть и умеет всё нужное.
- **APScheduler** — расписание живёт в том же рабочем цикле, что и задания.
- **Вебхуки, домен, Caddy** — polling не требует домена и TLS, а Telegram хранит апдейты ~24 часа.
- **LangChain / LlamaIndex** — пайплайн специфичный, абстракции будут мешать, и я не пойму, что внутри.
- **Отдельная векторная БД (Qdrant/Pinecone)** — на десятках тысяч записей это лишний компонент и лишняя точка отказа.
- **Kubernetes** — один сервис, один пользователь. Compose достаточно.
- **Мультиагентная архитектура** — один работающий пайплайн лучше пяти спорящих агентов.
- **OpenRouter** — берёт комиссию и прячет механику вызовов. Два прямых SDK за собственной абстракцией дешевле и дают нужный навык.
- **`user_id` в схеме** — один пользователь, YAGNI. Отказ фиксируется в ADR-0003.

## 3. Модель данных

Черновик. Финальная схема — после ADR-0003.

### Сырое (неизменяемо)
```
entries
  id, created_at, source (telegram|forward|api), kind (voice|text)
  raw_text, audio_path, duration_sec
  is_private, timezone, dedup_key
  meta jsonb          -- для source=forward: откуда, автор, дата исходного сообщения;
                      -- служебные идентификаторы Telegram, включая message_id ack-сообщения

entry_overrides       -- append-only смена состояния записи
  id, entry_id, action (hide|unhide|reclassify|make_private), payload jsonb, created_at
  актуальное состояние = последняя строка по entry_id
```
Права БД на `entries`: только INSERT и SELECT. UPDATE/DELETE отозваны.

### Производное
```
annotations          -- что LLM извлёк из записи
  id, entry_id, type, payload jsonb, model, state, created_at
  type: thought|task|event|loop|decision|error|insight|refusal|priority
  state: sure|two_hypotheses|unclear    -- enum вместо числовой уверенности

chunks               -- для поиска
  id, entry_id, text, embedding vector(768), tsv tsvector
  (приватные записи: tsv есть, embedding NULL, аннотаций нет вовсе)

links                -- связи между записями
  a_id, b_id, kind (related|contradicts), score, origin (vector|llm), confirmed_by_user

topics · entry_topics · rules   -- темы, привязка тем к записям, процедурная память
```

### Рабочие сущности
```
jobs          -- очередь: разовые задания, отложенные, повторяющиеся.
              Схему держит pgqueuer (своя миграция), мы её не изобретаем.
              Важно одно: таблица лежит в той же базе, поэтому задание
              ставится в одной транзакции с INSERT в entries (инвариант 7)
loops         entry_id, question, status, last_asked_at, times_asked
decisions     entry_id, decision, expected, confidence_pct, check_at, actual, outcome
reminders     trigger (time|event|topic), payload, fired_at, acked
touches       slot (morning|day|evening|weekly), sent_at, category
notion_sync   entry_id, page_id, synced_at, hash
llm_calls     наблюдаемость: модель, токены, стоимость, латентность, назначение
```

### Ключевые решения схемы
- **Провенанс:** у каждой производной записи `source_entry_id`. Без исключений.
- **Неизменяемость + оверрайды:** оригинал не правится никогда.
- **Задание и запись — одна транзакция** (инвариант 7). `jobs` живёт в той же базе именно ради этого.
- **Ретроактивная приватность:** разрешена. Удаляются `chunks.embedding` и аннотации, бот честно сообщает, что текст уже уходил во внешнюю модель.
- **Дедупликация:** `dedup_key` от содержимого + окна времени. Защита от двойной доставки Telegram.
- **Ретеншен аудио:** файл удаляется через 30 дней после расшифровки. Текст — вечно.
- **Семантическая память (`facts`) отложена за Фазу 6.** Пока её роль играют `annotations` + ретривал.
- **Размерность вектора — 768** (Gemini Embedding, срез MRL). Зафиксирована в схеме, менять больно: ADR-0006.

## 5. Настройка Claude Code

⏳ Claude Code развивается быстро. Перед настройкой свериться с https://docs.claude.com/en/docs/claude-code/overview

### 5.1. Что чем управлять

| Механизм | Для чего | Авторитет |
|---|---|---|
| **CLAUDE.md** | всегда нужный контекст проекта | модель может проигнорировать |
| **rules** | жёсткие ограничения | выше, чем CLAUDE.md |
| **skills** | переиспользуемые процедуры, грузятся по надобности | по требованию |
| **subagents** | делегированная работа в чистом контексте | изолированно |
| **hooks** | детерминированная автоматика на событиях | **не может галлюцинировать** |

**Правило:** всё, что критично, идёт в hooks, а не в CLAUDE.md. Модель может забыть инструкцию. Хук — не может.

### 5.2. CLAUDE.md (корневой)

Держать ~120 строк. Раздутый перестаёт работать. Содержимое:

- Что за проект, в трёх предложениях
- Стек с версиями
- Инварианты из раздела 1 — списком, явно
- Команды: `just dev`, `just test`, `just lint`, `just migrate`
- Стиль коммитов
- **Чего нельзя:** коммитить самому, пушить, менять миграции задним числом, добавлять зависимости без ADR
- Ссылка на `docs/adr/` — «перед изменением архитектуры прочитай решения»

### 5.3. Hooks (`.claude/settings.json`)

| Событие | Что делает |
|---|---|
| `PreToolUse` на Bash | блокирует `rm -rf`, `git push`, `git commit`, `alembic downgrade`, `docker compose down -v` |
| `PreToolUse` на Write/Edit | блокирует запись, если в содержимом похоже на секрет |
| `PostToolUse` на Edit/Write | `ruff format` + `ruff check --fix` + `mypy` по изменённым файлам |
| `Stop` | **быстрые** unit-тесты (без БД, LLM замокан) — сессия не заканчивается с красными тестами |
| `PreCompact` | предупреждение: «контекст переполняется, лучше `/clear` и новая задача» |

Блокировка `git commit` — намеренная. Коммичу я, руками, прочитав дифф.
Интеграционные тесты (живой Postgres) в хук не вешаем: он должен отрабатывать за секунды.

### 5.4. Permissions

- **Никогда не использовать `--dangerously-skip-permissions`.** Ни разу.
- Записи разрешены только внутри репозитория.
- Сеть — только на whitelist доменов.

### 5.5. Слэш-команды (`.claude/commands/`)

| Команда | Что делает |
|---|---|
| `/adr <тема>` | генерирует **шаблон** решения: проблема, 2–3 варианта, трейдофы. Заполняю и выбираю я |
| `/explain-diff` | объясняет последний дифф так, чтобы я мог пересказать |
| `/exam <модуль>` | задаёт мне 5 вопросов по модулю. Код не показывает. Отвечаю текстом |
| `/eval <набор>` | прогон eval-набора, сравнение с прошлым результатом |
| `/session-start` | сверка: где остановились, что в работе, какие тесты красные |
| `/check-versions` | проверяет актуальность версий зависимостей |

### 5.6. Субагенты (`.claude/agents/`)

- **`reviewer`** — критикует дифф в чистом контексте, до мержа.
- **`researcher`** — проверяет актуальность библиотек и API по документации, а не по памяти.
- **`test-writer`** — только тесты, не реализация.

### 5.7. MCP-серверы

Инструменты **для разработки**, не часть бота. Бот от MCP не зависит.

| Сервер | Зачем |
|---|---|
| **postgres** | Claude видит реальную схему и не выдумывает таблицы |
| **github** | issues, PR |
| **документация библиотек** | актуальные API вместо памяти модели. **Обязателен** |
| **playwright** | позже, если будет веб-интерфейс |

### 5.8. Проектные скиллы (`.claude/skills/`)

- **`migrations`** — как писать миграции: именование, обратимость, что нельзя менять задним числом

- **`adr-format`** — формат решений

## 6. Порядок первых шагов

Репозиторий, `docs/` и `docs/adr/0001–0007` уже есть. Блокеров не осталось: STT через API снял вопрос про ONNX-сборку и память, модель эмбеддингов выбрана.

1. `CLAUDE.md` и `.claude/settings.json` с хуками
2. MCP-серверы
3. `just` + `pyproject.toml` + `docker-compose.yml` (postgres — единственный сервис)
4. Коммит — руками, мной

## 8. Фазы разработки

Каждая фаза заканчивается **работающей вещью, которой я пользуюсь**. Сроков и оценок в днях нет намеренно.

### Фаза 0 · Скелет
Compose (postgres — единственный сервис), pgvector + pg_trgm, Alembic, FastAPI `/health`, CI (lint+tests), CLAUDE.md, хуки. ADR-0001…0007 написаны до начала фазы.
**Готово когда:** `docker compose up` поднимает всё, CI зелёный, есть одна пустая миграция.

### Фаза 1 · Захват
Бот принимает текст и голос (polling, два токена — dev и prod, whitelist `TELEGRAM_ALLOWED_USER_IDS`). STT через API за интерфейсом `core/stt`. Режим `/private on` принимает только текст: на голосовое отвечает отказом, наружу ничего не уходит. Мгновенный ack (<300 мс) отдельным сообщением; когда разбор готов, **это же сообщение редактируется** (`editMessageText`), а не отправляется новое — одна запись стоит одного уведомления. Значит, `message_id` подтверждения хранится в задании вместе с `entry_id`. Запись и задание — одной транзакцией. Рабочий цикл — pgqueuer (`SKIP LOCKED` + `LISTEN/NOTIFY`), с ретраями. Базовые напоминания по времени — та же очередь, без календаря. Удаление аудио через 30 дней.
**Готово когда:** неделю пользуюсь каждый день, ни одна запись не потеряна.
**Здесь же первый eval:** 20 своих голосовых, ручная разметка, WER. Сравниваются два подхода — аудио напрямую в мультимодальную модель против выделенного ASR-API. Корпус для него не нужен, поэтому он и первый.

### Фаза 2 · Поиск
Чанкинг (вся запись, если <1500 символов; длиннее — по абзацам и паузам с перекрытием ~15%), эмбеддинги (Gemini Embedding, 768 измерений — срез MRL), гибридный поиск: BM25 + триграммы (pg_trgm) + вектора, объединение через RRF. Команда «найди».
Третий канал — триграммы — не украшение: русский snowball без лемматизации плохо берёт словоформы, а смесь с английскими терминами ломает статистику BM25.
**Готово когда:** eval-набор из 50 вопросов размечен и recall@5 измерен. Набор собирается на реальном архиве, поэтому измерение делается в конце этой фазы или в начале Фазы 3, когда наберётся 100–150 записей. Без числа фаза не закрыта.

### Фаза 3 · Разметка
Дешёвая модель определяет тип записи, вытаскивает сущности и темы, возвращает состояние `уверен` / `две гипотезы` / `не понял`. Темы: сначала обязательная попытка попасть в существующую (top-K по эмбеддингу названий), новая — только с обоснованием. Провенанс, `entry_overrides`, ответ на запись с кнопками «не туда» и «сделать приватной».
**Готово когда:** eval классификации на 100 записях, точность измерена; выбор дешёвой модели подтверждён замером, а не прайсом.

### Фаза 4 · Касания
Планировщик (тот же рабочий цикл), категории сообщений, бюджет (3 инициативных касания в день; утренняя сводка вне бюджета), утренняя сводка, вечерний разбор, открытые петли, всплывание старого, кнопка паузы и «сегодня выходной». Адаптация к загруженности дня деградирует до «день не забит», пока нет календаря.
**Готово когда:** две недели сводки приходят вовремя и я их читаю.

### Фаза 5 · Календарь
**Здесь FastAPI впервые нужен по делу.** На Фазах 0–4 он держит одну ручку `/health` и больше ничего: адаптером служит Telegram, интерфейса у системы нет. С этой фазы появляется первый реальный HTTP-потребитель — OAuth-редирект Google.
Google Calendar: OAuth desktop-flow один раз, refresh token в `.env`. Читаем все календари, пишем только в отдельный календарь «Brain». Опрос раз в 5 минут. Отложенный контекст, сводка перед событием. Создание событий — только с подтверждением.
**Готово когда:** ни одно событие не создано без моего нажатия.

### Фаза 6 · Связи и витрина
**Здесь подключается дорогой тир:** ключ Anthropic Console и реализация `AnthropicProvider` в `core/llm`. До этой фазы ни одна задача дорогой модели не требует, поэтому платный ключ не заводится и вторая зависимость в проект не приходит. Интерфейс двухтирный с Фазы 1 — подключение сводится к реализации провайдера и строке в маршрутизаторе.
Связи (векторные, без LLM), противоречия (LLM только при близости выше ~0.85, только для мыслей и решений), стоп-лист, недельное ревью на дорогой модели, синхронизация в Notion: база «Записи» + страницы ревью, только записи с аннотациями, приватные — никогда.
**Готово когда:** первое ревью пришло и оказалось не бесполезным.

### Фаза 7 · Развитие
Журналы решений и ошибок, Фейнман, сократический режим, тестирование извлечением, приоритеты недели, живая шпаргалка.
Сюда же возвращается вопрос семантической памяти (`facts`): нужна ли она вообще, когда ретривал уже работает.

### Фаза 8 · Наблюдаемость · параллельно, поднимается раньше при боли
Стоимость по назначению, латентность по этапам, алерты, бюджетный потолок с деградацией (см. §9).

## 9. Экономика токенов

Не оптимизация, а требование к архитектуре.

1. **Не вызывать модель там, где хватает кода.** Парсинг времени, определение URL, дедупликация — код.
2. **Векторы вместо модели.** Поиск связей — ноль вызовов LLM (инвариант 8).
3. **Маршрутизация обязательна.**
4. **Батчинг.** Вечерняя разметка накопленного — одним вызовом на пачку; батч-API даёт скидку 50%.
5. **Кэширование системного промпта** — попадание в кэш стоит порядка 10% от обычной входной цены.
6. **Учёт с первого дня** — таблица `llm_calls`.
7. **Бюджетный потолок с деградацией.**

### Маршрутизация

| Задача | Модель |
|---|---|
| Классификация типа записи, теги, темы | дешёвая |
| Проверка противоречий | дешёвая |
| Сборка утренней сводки | дешёвая |
| Вечерний разбор | дешёвая (батчем) |
| Недельное ревью | дорогая · **с Фазы 6** |
| Диалог с архивом, сократический режим, Фейнман | дорогая · **с Фазы 6** |
| Эмбеддинги | Gemini Embedding (не тир, отдельный вызов) |
| Расшифровка голоса | STT-API |
| Поиск связей | **без модели** |

До Фазы 6 колонка «дорогая» пуста: ни одна задача Фаз 1–5 её не требует. Маршрутизатор в `core/llm` знает про два тира с первого дня, но дорогой тир до Фазы 6 не зарегистрирован — обращение к нему в этот период должно падать с явной ошибкой, а не молча уходить в дешёвую модель.

**При достижении потолка:** enrich уходит в отложенную очередь (записи сохраняются, разметка ждёт), дорогие режимы отключаются, приходит уведомление. **Захват не ломается никогда.**

Расход на старте, до Фазы 6: дешёвый тир ~$0.3–0.5 и эмбеддинги ~$0.2 в месяц. Полные $1.5–2.5 из бюджета — это состояние после подключения дорогого тира.

## 10. Evals — что и как мерить

| Набор | Что мерит | Метрика | Размер | Когда |
|---|---|---|---|---|
| STT | качество расшифровки моей речи; заодно выбор провайдера | WER | 20 голосовых | Фаза 1 |
| Retrieval | находится ли нужная запись | recall@5, MRR | 50 вопросов | конец Фазы 2 / начало Фазы 3 |
| Classification | верно ли определён тип | accuracy, матрица ошибок | 100 записей | Фаза 3 |
| Digest | полезна ли сводка | моя оценка 1–5 + LLM-судья | 10 сводок | Фаза 4+ |

Правила:
- Набор размечаю **я**, не модель. Иначе меряю модель моделью.
- **В CI автоматически — только детерминированные наборы:** STT, retrieval, classification.
- **LLM-судья — только вручную** через `/eval`, перед мержем существенных изменений промптов.
- Результат каждого прогона записывается. Ухудшение — блокер мержа.
- Начинать с малого: 20 примеров лучше, чем ноль.

## 11. Риски

| Риск | Митигация |
|---|---|
| STT-провайдер плохо берёт русский с англ. терминами | eval на своих голосовых в Фазе 1, до того как строить на нём. Два кандидата сравниваются сразу |

| Провайдер обновил модель — промпты поехали | детерминированные eval-наборы в CI ловят регрессию |
| Бросаю через месяц | фаза 1 даёт ежедневную пользу; кнопка паузы; долг не копится |
| Стоимость растёт незаметно | `llm_calls` с фазы 1, бюджетный потолок с деградацией. Аудио — единственная статья, растущая с использованием: следить по факту |
| Скоуп разрастается | `vision.md` — единственный источник фич. Новая идея → в архив, не в код |
| Потеря данных | `pg_dump` + gzip раз в сутки в объектное хранилище, шифрование бэкапа ключом вне сервера, **проверка восстановления раз в месяц**. Непроверенный бэкап = нет бэкапа. Аудио не бэкапим |
| Компрометация сервера = доступ ко всему | принято осознанно, фиксируется в ADR-0002. Шифрование диска VPS и бэкапов ключом, который не лежит на сервере |
| Очередь на Postgres упирается в нагрузку | при двух десятках заданий в день это неактуально; упрёмся — вынесем отдельно. Ровно тот случай, ради которого действует правило «начинаем с минимума» |
| Понимаю всё хуже, чем кажется | `/exam` раз в неделю ловит это рано |

### Деплой

Код пушу я в GitHub, на сервере `git pull && docker compose up -d --build`. Миграции — **отдельной командой в том же шаге, не автоматически при старте контейнера**: автомиграция на старте это классическая мина. Позже — GitHub Actions.

**Два окружения — два бота.** Локально запускается dev-бот, на сервере prod-бот; токены разные, базы разные. Оба бота бесплатны, заводятся у @BotFather. Смысл — отладка не портит реальный архив: у dev-бота свой чат, своя история и своя база, а перепутать их нельзя, потому что токен приходит из `.env` соответствующего окружения. Whitelist `TELEGRAM_ALLOWED_USER_IDS` работает у обоих: всё, что приходит не от меня, игнорируется молча.
