# ADR-0008 · Схема pgqueuer внутри Alembic

**Статус:** принято · **Дата:** 15 августа 2026
**Связанные:** [0005](0005-queue-on-postgres.md) (очередь), [0003](0003-schema-and-append-only.md) (схема и права), [0001](0001-stack.md) (Alembic с первого дня)

---

## Контекст

[ADR-0005](0005-queue-on-postgres.md) выбрал pgqueuer, но записал неточность: «схему держит pgqueuer своей миграцией». Своей истории миграций у pgqueuer нет. Схема ставится командой CLI — `pgq install`, обновляется `pgq upgrade`, сносится `pgq uninstall`, проверяется `pgq verify`. Версия схемы нигде не записана: библиотека определяет состояние, заглядывая в `information_schema`.

Ставится при этом не одна таблица. В 1.3.2 это enum `pgqueuer_status`, четыре таблицы (`pgqueuer`, `pgqueuer_log`, `pgqueuer_statistics`, `pgqueuer_schedules`), их индексы, функция `fn_pgqueuer_changed` и триггер `tg_pgqueuer_changed` — около 116 строк SQL.

У нас же Alembic с первого дня и жёсткое правило: миграции только вперёд, `alembic downgrade` запрещён, применённая миграция задним числом не правится. Вопрос в том, как эти два механизма уживаются в одной базе.

Вопрос не абстрактный. Пока схему ставит отдельная команда, состояние базы не выводится из репозитория: `alembic upgrade head` даёт одну базу на машине разработчика и другую на сервере, если про вторую команду забыли. Обнаруживается это в момент, когда воркер не может поставить задание.

## Варианты с трейдофами

### Ось 1. Чем ставится схема очереди

| Вариант | За | Против |
|---|---|---|
| **SQL из `pgq sql install` внутрь Alembic-ревизии** — выбран | одна история миграций; `alembic upgrade head` приводит базу в полное состояние; запрет отката распространяется и на очередь; чужой DDL виден в дифе при ревью | SQL прибит к версии библиотеки: апгрейд pgqueuer требует ручного шага |
| `pgq install` отдельной командой | ноль ручной работы, всегда соответствует версии библиотеки | состояние базы не выводится из репозитория; два механизма и два порядка применения; `pgq uninstall` живёт мимо запрета на откат |
| `Queries.install()` при старте приложения | ничего не надо помнить | DDL на старте процесса — гонка при нескольких процессах и молчаливое изменение схемы в проде |

`pgq sql install` для этого и предназначен: команда не подключается к базе и печатает детерминированный SQL с точками с запятой — в документации она прямо названа пригодной для сохранения в файл миграции.

### Ось 2. Где лежат объекты очереди

| Вариант | За | Против |
|---|---|---|
| **В `public` рядом с нашими таблицами** — выбран | ничего не надо настраивать: ни `search_path` в соединении, ни отдельной цели в Alembic. Объекты и так узнаваемы по имени — все начинаются на `pgqueuer` | чужие таблицы вперемешку со своими в списке `\dt` |
| Отдельная схема через `--schema pgq` | визуально чисто | `search_path` придётся протаскивать в каждое соединение и в Alembic; за чистоту списка таблиц платим настройкой в трёх местах |

`PGQUEUER_PREFIX` не используем: он нужен для нескольких независимых очередей в одной базе, у нас она одна.

## Решение

**Схема pgqueuer ставится Alembic-ревизией, тело которой — вывод `pgq sql install`.** Объекты живут в `public`. Команда `pgq install` в проекте не используется никогда — ни локально, ни на сервере.

**Обновление библиотеки — новая ревизия из `pgq sql upgrade`**, как и любое другое изменение схемы. Правило «только вперёд» действует без исключений: `pgq uninstall` в проекте запрещён так же, как `alembic downgrade`.

**Порядок при апгрейде pgqueuer:**

1. поднять пин версии в `pyproject.toml`;
2. `uv run pgq sql upgrade` — получить SQL;
3. новая Alembic-ревизия с этим SQL в `upgrade()`;
4. `uv run pgq verify --expect present` на накатанной базе — сверка того, что библиотека видит схему своей версии.

Шаг 4 — единственная защита от расхождения между кодом библиотеки и состоянием базы, потому что версии схемы pgqueuer нигде не хранит.

## Цена решения

- **Ручной шаг при каждом апгрейде pgqueuer.** Забудешь сгенерировать ревизию — библиотека новая, схема старая, и узнаем об этом по ошибке в рантайме. Смягчается `pgq verify`, но выполнять его надо не забыть тоже.
- **116 строк чужого DDL в нашей истории миграций.** Мы их не писали и построчно читать не будем — правило «через полгода объяснить любой модуль» на эту ревизию не распространяется, и это сознательное исключение.
- **`downgrade()` в ревизии будет формальным.** Тест `test_every_migration_defines_downgrade` требует его наличия, но выполнять его нельзя — как и у любой другой нашей миграции.
- **Расхождение с апстримом при смене формы SQL.** Если pgqueuer переименует объекты или поменяет структуру, наш дифф это покажет — но принять изменение придётся вручную.
- **Объекты очереди в `public`.** Список таблиц смешанный. Если когда-нибудь понадобится их изолировать, переезд будет означать перенос данных очереди, а не переключение флага.
