# ADR-0003 · Схема данных и append-only

**Статус:** принято · **Дата:** 15 августа 2026
**Связанные:** [0002](0002-privacy.md) (пишется в паре с этим), [0005](0005-queue-on-postgres.md) (инвариант долговечности), [0006](0006-retrieval.md) (размерность вектора в схеме)

---

## Контекст

Первый принцип проекта: **сырое неизменяемо**. Выжимка не заменяет оригинал, а лежит рядом; текст записи не меняется и не удаляется никогда. Это не техническое требование, а суть инструмента — система, которая может незаметно переписать мою мысль, не заслуживает доверия, и я перестану ей пользоваться.

При этом состояние записи меняется постоянно: запись скрывают, переклассифицируют, помечают приватной задним числом. Модель ошибается, я поправляю. Нужен способ менять состояние, не трогая содержимое.

Отдельно: у каждой производной сущности должно быть видно, откуда она взялась — иначе через год невозможно отличить то, что я сказал, от того, что вывела модель.

## Варианты с трейдофами

### Ось 1. Как менять состояние записи

| Вариант | За | Против |
|---|---|---|
| **`entries` только INSERT + `entry_overrides` append-only**, актуальное состояние = последняя строка по `entry_id` — выбран | оригинал неприкосновенен физически (права БД), история изменений бесплатна, откат тривиален | чтение состояния требует оконной функции или `DISTINCT ON` и индекса; таблица оверрайдов растёт |
| Обычный CRUD с `UPDATE` | простые запросы, привычно | одна ошибка в коде — и запись переписана без следа. Прямо нарушает принцип 1 |
| Полное темпоральное версионирование каждой таблицы (SCD2) | история везде | сложность на порядок выше при пользе только для `entries`; каждый запрос обрастает фильтром по валидности |
| Event sourcing целиком | максимальная восстановимость | проекции, их пересборка, отладка — отдельный проект. Двадцать записей в день этого не оправдывают |

### Ось 2. Мультипользовательность

| Вариант | За | Против |
|---|---|---|
| **Без `user_id`** — выбран | схема проще, запросы короче, ни одного лишнего индекса | если пользователей когда-нибудь станет больше одного, это миграция всех таблиц разом |
| `user_id` везде «на всякий случай» | готовность к росту | YAGNI: рост не планируется, а цена платится каждый день в каждом запросе |

### Ось 3. Семантическая память (`facts` — триплеты субъект-предикат-объект)

| Вариант | За | Против |
|---|---|---|
| **Отложить за Фазу 6** — выбран | вопрос «что я знаю про X» решается ретривалом по `annotations` уже в Фазе 2 | до момента, когда триплеты действительно понадобятся, их не будет |
| Строить сразу | красивая модель знаний | нормализация сущностей («Маша» = «Мария Ивановна» = «она») — отдельный проект на недели, дающий шум при плохом качестве |

### Ось 4. Как модель сообщает уверенность

| Вариант | За | Против |
|---|---|---|
| **enum: `уверен` / `две гипотезы` / `не понял`** — выбран | различимые состояния, каждому соответствует своё поведение системы | грубее числа |
| Число 0–100 | кажется точнее, удобно сортировать | числовая самооценка у моделей плохо калибрована: 0.85 и 0.7 не значат ничего устойчивого |

## Решение

### Сырое (неизменяемо)

```
entries
  id, created_at, source (telegram|forward|api), kind (voice|text)
  raw_text, audio_path, duration_sec
  is_private, timezone, dedup_key
  meta jsonb   -- для source=forward: откуда, автор, дата исходного сообщения;
               -- служебные идентификаторы Telegram, включая message_id ack-сообщения

entry_overrides   -- append-only смена состояния
  id, entry_id, action (hide|unhide|reclassify|make_private), payload jsonb, created_at
```

**Права БД на `entries`: только INSERT и SELECT. UPDATE и DELETE отозваны** — запрет живёт в базе, а не в договорённости.

### Производное

```
annotations   id, entry_id, type, payload jsonb, model, state, created_at
              type: thought|task|event|loop|decision|error|insight|refusal|priority
              state: sure|two_hypotheses|unclear
chunks        id, entry_id, text, embedding vector(768), tsv tsvector
links         a_id, b_id, kind (related|contradicts), score, origin (vector|llm), confirmed_by_user
topics · entry_topics (entry_id, topic_id, confidence) · rules
```

### Рабочее

```
jobs (схема pgqueuer) · loops · decisions · reminders · touches · notion_sync · llm_calls
```

### Инварианты схемы

1. **Провенанс обязателен:** у каждой производной записи `source_entry_id`. Без исключений.
2. **Оригинал не правится никогда.** Смена состояния — строкой в `entry_overrides`.
3. **Запись и задание в очередь — одна транзакция** (см. [ADR-0005](0005-queue-on-postgres.md)).
4. **Приватная запись:** `tsv` есть, `embedding` NULL, аннотаций нет (см. [ADR-0002](0002-privacy.md)).
5. **Дедупликация** по `dedup_key` от содержимого и окна времени — защита от двойной доставки Telegram.
6. **Ретеншен:** аудио удаляется через 30 дней после расшифровки, текст — вечно.
7. **`rules`** (процедурная память) редактируются через бота и попадают в промпты отдельным блоком системного сообщения, собираемым в `core/llm`.

## Цена решения

- **Каждое чтение состояния дороже.** «Актуальная запись» — это не `SELECT * FROM entries`, а джойн с последней строкой оверрайдов. Нужен индекс `(entry_id, created_at DESC)` и дисциплина: чтение состояния живёт в одном месте `core/memory`, иначе оконная функция расползётся по коду.
- **Опечатка живёт вечно.** Исправить текст записи нельзя — только перекрыть оверрайдом. Оригинал с ошибкой остаётся в базе навсегда, и это осознанно.
- **Таблица оверрайдов растёт независимо от полезного содержимого.** На нашем объёме это неощутимо, но механики очистки нет и не планируется.
- **Отозванные UPDATE/DELETE усложняют миграции.** Любая операция, которой действительно нужно тронуть `entries` (например, зачистка `audio_path` по ретеншену), требует отдельной привилегированной роли и явного решения. Мина спрятана здесь: соблазн «временно вернуть права» будет, и поддаваться ему нельзя.
- **Отказ от `user_id` — билет в один конец.** Появление второго пользователя означает миграцию всех таблиц, всех индексов и всех запросов разом. Записано именно для того, чтобы через год было понятно, что это выбрали, а не забыли.
- **`facts` откладываются — значит, «что я знаю про X» отвечает ретривал**, то есть ответ будет списком релевантных записей, а не собранным профилем. До Фазы 7 живём с этим.
- **enum вместо числа** лишает сортировки по уверенности: нельзя показать «десять самых сомнительных разборов». Взамен каждое состояние однозначно отображается в поведение — молча сохранить, спросить сразу или отложить в вечерний пакет.
- **`payload jsonb`** в аннотациях и оверрайдах — гибкость, купленная отсутствием проверки на уровне БД. Схему содержимого держат Pydantic-модели, и рассинхрон между ними и накопленными данными — реальный риск при эволюции.
